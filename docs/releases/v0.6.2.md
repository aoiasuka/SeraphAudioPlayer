# Seraph Audio Player v0.6.2

本版本是一个 **歌词解析模型审计与性能专版**：用本机 1 279 份真实 QQ 音乐加密 QRC 缓存与 LDDC 样本对解析器做了全量筛查，修正了 9 处解析与显示缺陷，把解析链路的热点重写为无分配的单趟实现，并修好了「检查更新」里「前往下载」按钮自 v0.5.7 起一直失败的问题。

## 修复

### 更新功能

- **「前往下载」与「在资源管理器中显示」失败**：两处都通过 `System32\explorer.exe` 启动资源管理器，而 Windows 上 explorer 的本体只在 `%SystemRoot%\explorer.exe`（System32 下没有），v0.5.7 的加固把路径写错后这两个按钮一直静默失败。现按真实位置解析，并加入回归测试在 Windows 上实测该路径存在。检查更新本身不受影响（本机已用生产同款网络配置实测）。
- **限流提示**：匿名 GitHub 接口每 IP 每小时 60 次，超限时现提示「请求过于频繁，请稍后再试」而不是裸状态码。

### 歌词解析

- **QRC 元数据里的未转义引号截断歌词**：`[al:THE BEST "Blue"]` 这类直引号会让容器内容在第三行就被截断，整首歌解析为空、再误走 KRC 路径输出带 `(毫秒,时长)` 标签的行级垃圾文本。真实缓存 1 279 份里有 24 份受影响（含 Michael Jackson、Linkin Park、Aimer、milet 等），现全部解出逐字。
- **YRC 文本含 `<` 时被误判为 KRC**：此前只要文本里出现 `<`（如 `<3`）就先走 KRC 解析，找不到 `<offset,dur,0>` 标签时把整行连同 `(start,dur,0)` 标签当纯文本返回；现在 KRC 的判据是至少存在一个三元组音节标签。
- **TTML 纯空白音节丢失**：`<span> </span>` 这类空白音节此前被整个过滤，音节拼接变成「Helloworld」，逐字高亮丢掉词间空格；现与 QRC / 增强 LRC 同口径——空白并入前一音节并延长其时间。`<br/>` 现按一个空格处理，不再让前后文本粘连。
- **HTML 实体解码两次与数字实体不识别**：链式替换会把 `&amp;lt;` 解成 `<`；QQ 网页端返回的 `&#8217;` 一类数字实体此前原样显示。现单趟解码、只解一层，并支持 `&#NNN;` / `&#xHH;`。
- **双语 LRC 音译行在前时主句错位**：LDDC 默认按「音译、原文、译文」顺序写文件，此前同起点组以第一行为主句，罗马音被当成大字主句、原文降级成小字且失去逐字高亮。现在同起点组里带逐字时间轴的那行做主句，都没有时保持文件顺序。
- **QQ 音译轨丢失逐字时间轴**：QQ 的 `roma` 是逐字 QRC，并入原文行时只保留了文本；现连同音节时间轴一起存进 `roman.words`（尚未渲染，为后续逐字音译预留）。
- **QQ 译文里的版权声明行**：「QQ音乐 / TME 享有本翻译作品的著作权」此前作为译文附在首句上，现与 `//` 占位一并剔除。
- **单行上限不覆盖音节与副轨**：W-01 的 512 字符上限此前只钳整行文本，音节、译文、音译不受限，恶意输入仍能让逐字渲染产生上千个节点；现音节按累计字符截断、译文最多 4 轨且每轨同上限、音译同上限。
- **忽略文件 offset 的极端值溢出**：`display` 还原 offset 时改用饱和加法，`u64::MAX` 起点配合 `i32::MIN` offset 不再触发整数溢出。

## 性能

解析链路按合成基准（300 行 × 24 音节，`npm run benchmark:lyrics`，同机同构建）与真实语料实测：

| 场景 | v0.6.1 | v0.6.2 | 提升 |
| --- | ---: | ---: | ---: |
| 增强型 LRC（600 行，含双语） | 8.3 ms | 2.3 ms | 3.6× |
| 逐行 LRC | 0.51 ms | 0.15 ms | 3.3× |
| QRC 容器文本 | 10.2 ms | 5.2 ms | 2.0× |
| YRC | 7.0 ms | 1.3 ms | 5.6× |
| KRC（含译文表） | 7.2 ms | 1.6 ms | 4.4× |
| TTML（含译文 / 音译） | 6.5 ms | 3.9 ms | 1.7× |
| QQ 云端加密 QRC（解密 + 解析） | 16.2 ms | 5.9 ms | 2.7× |
| 本地加密 `.qrc`（解密 + 解析） | 16.7 ms | 5.9 ms | 2.8× |
| 曲库歌词 JSON 反序列化（50 份文档） | 106 ms | 66 ms | 1.6× |
| 无 BOM UTF-16 增强型 LRC | 7.8 ms | 2.1 ms | 3.8× |

真实语料：1 279 份 QQ 加密 QRC（3.7 MB）从 2.0 s 降到 0.44 s（4.5×），解析结果除上述缺陷修复外逐文件指纹一致。

- **文本清洗单趟化**：音节与整行清洗此前是「剥标签 + 9 次链式 `replace` + 折叠空白」，每个音节分配十来次；现为单趟扫描，已是清洗态的输入直接借用不复制。
- **无分配的时间标签与元组解析**：LRC 时间标签、`(a,b,c)` 元组判定不再为每个标签分配临时字符串 / 向量；`contains_tuple_marker` 找到首个即停，不再收集整篇。
- **字节解码借用**：UTF-8 输入不再复制一份；无 BOM 的 UTF-16 嗅探只看开头 8 KB，不再为 4 MB 文件扫两遍全文。
- **QQ 变体 3DES 查表化**：IP / FP / E 按字节查表，S 盒与 P 置换合成 8 张表，密钥展开只做一次；单块从约 4 600 次逐位取放降到约 400 次查表，已知答案向量（真实密文块、多块往返、单 DES）全部保持。
- **曲库歌词文档流式反序列化**：`LyricDocument` 兼容旧数组与新对象两种形态，此前经 `untagged` 枚举先把整份输入缓冲成中间树再逐个变体尝试；现按首个 token 直接分派，大曲库加载的耗时与峰值内存随之下降。
- **本地歌词目录匹配**：曲目侧的曲名 / 艺术家归一化在整个目录扫描里只算一次（此前每个候选文件重算 4 次）；KRC 译文按起点建索引。
- **逐字高亮不再牵动整篇列表**：平滑时钟（rAF 每帧外推）此前由歌词面板持有，每一帧都让侧栏 / 沉浸页的几百行歌词整体重渲染；现移入当前行的 `KaraokeLine` 内部，父组件只随后端进度事件（约 10 Hz）重渲染。

## 工程化

- 新增 `npm run benchmark:lyrics`：合成 LRC / 增强 LRC / QRC / YRC / KRC / TTML / 加密 QRC / 曲库 JSON 的解析微基准，走生产解析函数，输出到 `target/optimization-lyrics-benchmark.json`。
- 新增 `#[ignore]` 的联网探针 `live_github_release_lookup`，排查「检查更新失败」时用生产同款 client 真查一次。
- 回归覆盖：前端 309 → 310，Rust 379 → 394。

## 安全边界

- 没有新增出站 client 或命令；`explorer.exe` 仍走绝对路径（F-05），只是改为真实位置。
- 解析上限（行数 / 单行 / 音节 / 副轨 / 解密输入）只收紧未放宽；QRC 容器正则的收尾改为 `"` + 可选空白 + `/>`，仍要求内容以引号结束。

## 兼容性

- 无数据格式变更；曲库清单仍为版本 2。`LyricText.words` 开始被 QQ 音译轨使用，旧程序读取时忽略该字段。
- 已入库的歌词不会自动重新解析；受上述 QRC / TTML 缺陷影响的曲目重新导入或在线匹配后即可获得修正结果。
